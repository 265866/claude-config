### Hillclimb

**You own the metric and the experiment's integrity. Supervise and review.** For sustained, iterative improvement of one measurable thing against a target. A one-off fix is Bug fix or Perf issue. Choose execution using [the execution reference](../references/execution.md).

Core discipline: one change, one measurement, keep or revert. Never stack untested changes, and never claim a win from code inspection (the **principle-prove-it-works** skill).

1. Ground the workload and architecture before choosing the metric. Run the **how** skill over the target, name the realistic workload dimensions that can move the result (data size, history, state, concurrency), and select a case that reproduces the user's complaint. If no case reproduces it, fix the repro instead of hillclimbing. Fix one metric, the direction that counts as better, a checkable target, and a bounded attempt/retry budget with a no-progress condition. Use the user's numbers when given, otherwise agree material target choices. Repeat measurements enough to distinguish a win from noise; do not invent a minimum number of code changes after a verified target is met.
2. Build the measurement harness, prove its sensitivity, then freeze it (the **principle-build-the-lever** skill). Run contrasting realistic workloads and confirm the target case reproduces the symptom while easier cases separate as expected. If the harness cannot distinguish them, revise the workload or metric. For a perf metric, vet the harness with the **benchmark-checklist** skill before you freeze it. For any other metric, vet it with **principle-explain-the-number**. Either way, make it print its error count and a work count. The work count counts the results the workload must deliver, such as requests answered or rows written, not internal operations that a change may skip or prune. When the metric measures the interactive path, make the harness wait for the workload's deferred work to finish and read the work count then, outside the timed region. Make it alternate before and candidate runs, at least 5 of each, and print each run's value, the median, and the range. The before side is a parameter: the last kept version for each attempt, and the original baseline for the final number. Once frozen, one repeatable command emits the metric. Record the baseline metric and a green run of the regression gate (the tests that must keep passing) before any change.
3. Open the canonical decision log via the **show-me-your-work** skill and its helper; let that skill own the format and location. For each attempt, link evidence artifacts recording the hypothesis, change, before/after measurements, delta, regression-test results, and kept/reverted verdict. Read the log before each attempt.
4. Ground each hypothesis in the architecture model from step 1, so it names a specific mechanism ("defer X off the boot path because it blocks first paint"), not "try memoizing something". For a perf metric, order hypotheses by the performance mantras in step 2 of the [Perf issue](perf-issue.md) playbook. Borrow their order, caveats, and signal rule, but not that step's stop rule. Mantra 5 earns an attempt only when the frozen metric measures the interactive path. The signal comes from a trace or profile taken in a run you do not report, per **benchmark-checklist** question 1. Take a new one after each kept change. Steps 6 and 7 decide when to stop.
5. Loop, one hypothesis per iteration:
   - Implement or delegate one tightly scoped attempt through the selected method, inheriting the configured model and effort. Substantial repeated attempts fit a bounded native work/measure/check cycle. Independent hypotheses can use isolated worktrees (the **principle-separate-before-serializing-shared-state** skill); experiments sharing a measurement environment run serially. Review the diff and obtain fresh-context review for non-trivial accepted implementation.
   - Measure before and after with the frozen harness, and run the regression gate. Each keep-or-revert checks the error and work counts. Only a median gap in the target direction counts. It moves past noise when it is larger than both sides' ranges. When it falls between the ranges, or one run is an outlier, a rank-sum test or the harness's own statistics decides. For a perf metric, these are **benchmark-checklist** questions 4, 7, and 5, and the final number gets the full checklist. For any other metric, vet the final number with **principle-explain-the-number**. Take the final number from runs that alternate the original baseline with the final version, and report the baseline from those runs.
   - Accept only when the error count is no higher than the before side's, the work count is no lower, the metric moves past noise (or, for a change that only simplifies code, shows no gap past noise in the wrong direction), and the gate stays green. Otherwise revert the change in full. A tweak that "might help" is not kept.
   - One commit per accepted fix, prepared with the **commit-agent** agent and scoped to the files that attempt changed. Log the row either way, kept or reverted.
   Follow **principle-sequence-verifiable-units**: measure and check each hypothesis before acceptance or dependent work. Independent isolated attempts can run in parallel, while shared measurement stays serial; verify the combined artifact before accepting integrated changes. Scheduled wakes supervise external waits; they do not implement the experiment loop. Hold a hypothesis that would override a design the user chose or needs an ask-first action until it is resolved; independent hypotheses continue.
6. Push past the first plateau. On a stall, several rejects in a row, pivot to another mantra or mechanism, combine near-misses, re-read the source, or try something more radical before concluding the hill is climbed. Correctness and simplicity outrank the number. Revert a win that breaks behavior, and keep a simplification that holds the number (the **principle-laziness-protocol** skill).
7. Stop successfully when the predicate is met. At the no-progress limit, revise the hypothesis from evidence before another bounded cycle. Report a blocker, exhausted budget, or marginal remaining ideas without claiming the target was achieved. Do not relax the predicate or leave unverified changes behind.
8. Run **Opening a PR** only when creation is explicitly requested or approved, with accepted commits in their verified order.

**Reply:** after anything waiting on the user, lead with whether the target was met and, for a perf metric, the **benchmark-checklist** verdict. Then give the metric and target, baseline to final with the percent delta, run count, and range, iterations run (kept vs reverted), each accepted fix on one line, the canonical decision-log path, and the best idea you would try next if pushed further. For a perf metric, also give the limiter.
