### Bug fix

**You own this task. Plan, review, verify.** Choose execution using [the execution reference](../references/execution.md).

Be scientific. Every shipped line traces to runtime evidence. Belt-and-suspenders that "might help" is a hypothesis, not a fix. It does not ship. When evidence refutes a hypothesis, revert what it motivated. The smallest change the evidence justifies ships. This limits speculation, not coverage: another proven defect found along the way that CLAUDE.md (Authorization and ownership) puts in scope, or a boundary safeguard (**principle-boundary-discipline**) against a failure mode that a reproduction, test, or traced code path demonstrates, is evidence-backed and ships as its own verified unit. A guard that hides the root cause never ships.

1. Reproduce it yourself on the matching surface via the matching control-ui or control-cli skill (CLAUDE.md, Procedure triggers), even when a debug or instrumentation protocol says to ask the user to reproduce. Ask the user only with a stated, specific reason the control surface cannot reach the target, and only after driving it as far as it goes. If it won't reproduce directly, synthesize the trigger, tighten conditions, or instrument until it fires.
2. Binary-search the cause. Form the candidate hypotheses, then rule them out until one survives. Ground them with `how` over the affected subsystem; use **why** when regression history can discriminate between them. Each pass, take the split that cuts the most remaining problem space, get runtime evidence, eliminate. When program state is unclear, add instrumentation or logging and read it as the code runs. Don't guess. Use bounded investigation/check rounds for a stubborn hunt, with a no-progress condition and a revised hypothesis before retrying. Timed wakes are for external evidence, not computation. Confirm the surviving *mechanism* with runtime evidence before design or implementation.
3. Plan the smallest justified fix. Use `architect` for a material unsettled design, not merely a change crossing a function boundary. Execute directly or delegate a bounded unit with exact ownership through the selected method. Use dependent phases or a bounded repair cycle when their coordination is substantial, inheriting the configured model and effort. Split the run before a user decision; obtain fresh-context review for non-trivial implementation. When step 5 uses **tdd**, write its regression test and confirm it fails before implementing the fix.
4. Verify on the same surface. The original repro now passes. "Inconclusive" or wrong-surface is not a pass. Flag it. Unit tests show branch behavior, not bug absence.
5. Preserve evidence that the regression failed before the fix and passed afterward. Use the **tdd** skill to demonstrate the failing regression first when the user asked for a failing or regression test or the bug has a cheap local test path; otherwise retain the real reproduction evidence. Follow **principle-sequence-verifiable-units** for delivery: the regression and fix form a self-contained, passing change rather than requiring a broken commit.
6. Run **Opening a PR** only when creation is explicitly requested or approved. Otherwise deliver the verified local fix.

**Reply:** what was broken, root cause, fix, how you verified. Paste failing-then-passing repro output verbatim.
