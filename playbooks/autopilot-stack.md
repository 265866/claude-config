### Autopilot-stack

Build and verify a dependent linear stack for the operator to review and land. This differs from autopilot-full: dependencies are retained, and merge-ready delivery is the default stopping point.

1. Frame the base branch, units in dependency order, owner/file boundaries, done predicate and explicit action grants. Record which units genuinely depend on earlier changes.
2. Choose execution through [the execution reference](../references/execution.md). Native dependent phases fit substantial stacks; small settled units can run directly or through ordinary delegation. Assign one owner per unit and inherit the configured model and effort. Supply each dependent writer the exact accepted parent SHA. With native worktree isolation, the writer must establish and verify that SHA inside its actual generated worktree before editing; the API has no exact-base flag. Alternatively, use a prepared worktree without automatic isolation and require the writer to verify its base. Preparing the parent checkout does not establish a generated child's base, and parent uncommitted changes do not transfer. Independent exploration can run in parallel; writers sharing a branch cannot.
3. Owners implement with real happy/edge/regression checks, clean-code and a show-me-your-work trail. Return the worktree path, uncommitted diff, trail path and receipts before integration. Owners cannot delegate, so the coordinator runs review-comments (with its independent comment-reviewer) and the trail's independent review on each returned unit, then runs the commit-agent agent in that worktree and records the unit's local commit/head. Opening a ready or draft PR follows the operator's explicit request through opening-a-pr.
4. One integrator assembles the linear stack and records branch/base/head relationships. Keep each unit independently reviewable. Never weaken or remove checks to make the stack green.
5. The coordinator runs independent swarm review at code-ready heads under the selected execution method. Scale live-surface and performance checks to the actual change, with one owner for a shared UI session or measurement environment. Fix real findings in the lowest unit that owns them and re-check every affected dependent head.
6. Observe CI and review through babysit. Prepare replies before asking to post them. End the current native run before that ask-first action; continue independent work, and start the dependent stage after approval; the graph does not wait for a mid-run user decision. Pushes to the stack's own branches (including `--force-with-lease=<branch>:<sha you last pushed to it>` after a restack, while nobody else has pushed to that branch) and retargeting PRs the task owns proceed and get reported. Opening a PR or issue and posting follow the ask-first actions in CLAUDE.md (Authorization and ownership).
7. Deliver the contiguous verified stack and its exact-head evidence. Leave it merge-ready for the operator. If the user subsequently authorizes landing, use shipping bottom-up.
8. Reconcile children and record any stale verdicts, blocked checks, or unverified units. A green top PR cannot hide an unsafe lower unit.

Use autopilot-full when changes are independent and the operator explicitly wants each approved PR merged. Use this playbook when changes form a dependency chain. Independent changes use autopilot-full, which can also stop at merge-ready when the operator keeps the landing decision.

Native execution owns active workers and within-run results; the Markdown plan retains design and acceptance, Tasks displays coarse milestones, and the project ledger retains branch dependencies and exact-head receipts. Missing or failed workers remain explicit gaps rather than completed units. When the user pauses, follow [Pause safely](pause-safely.md). Its step 3 keeps work that has not passed this playbook's step 3 review route, and withdrawn or blocked-by-withdrawal work, out of the checkpoint. When the user withdraws authorization for one unit's work, stop that unit's code and branch writes, CI reruns, PR creation and edits, replies, and merges at once. Record the withdrawn unit itself, with its branch and PR, as withdrawn in the project ledger. Record each unit that depends on it as blocked by withdrawal there too, and hold each such unit as that [resume mark](pause-safely.md#resume-marks) says, with its writer stopped where it is. When the user withdraws authorization for the stack, stop every unit's code and branch writes, CI reruns, PR creation and edits, replies, and merges at once. Handle each withdrawn or blocked-by-withdrawal unit's armed auto-merge or queued PR as the [Withdrawn resume mark](pause-safely.md#resume-marks) says. Whether the user withdrew one unit or the whole stack, leave a half-done operation, such as a rebase, in a withdrawn or blocked-by-withdrawal unit as it is, because aborting it would discard its in-progress work. Report it and record it in the project ledger as withdrawn, or as blocked by withdrawal when it belongs to a blocked-by-withdrawal unit. When a half-done operation stays in a repository, write a one-line pointer to that ledger under the repository's `claude-pause/`, as Pause safely step 4 says, so a later session finds the mark. Leave withdrawn work uncommitted and list its files in the project ledger as withdrawn.

**Reply.** Stack order, bases and heads, verification receipts, review findings and fixes, current merge-ready frontier, withdrawn units and their files, any half-done operation left in place, any auto-merge disabled, still armed, or queued on withdrawn or blocked-by-withdrawal work, the units a withdrawal blocked, and the remaining operator actions.
