### Babysit

Observe and, within the authorized scope, drive a PR or its stack frontier toward merge-ready. Merely opening a PR does not start this workflow.

1. Declare the requested mode. A status question is read-only. A request to address checks or review authorizes scoped local fixes; remote replies, edits, pushes and merges still follow the root per-action authorization policy. A sustained watch needs a concrete exit condition and deadline.
2. Read the actual PR/base/head relationships, required checks, reviews and unresolved threads. Work on the lowest unmerged dependency first. Read upper-stack feedback without restarting a failing frontier's checks to fix unrelated upper work.
3. For one status snapshot, resolve the profile and use `bun "<profile>/tools/workflow/watch-pr/watch-pr.ts" --owner <owner> --repo <repo> --pr <number> --status-only`. For an explicitly requested watch, supply a bounded `--timeout`, such as `--timeout 1800`, and supervise its output with native Monitor or a bounded process wait. Do not launch an unobserved watcher with its unbounded default.
4. Connected stacks use `--stack`. An explicitly captured immutable merge queue uses `--queued-stack --stack-prs <bottom-to-top numbers>`. Do not switch modes implicitly or treat incomplete queries as readiness. If the graph or available metadata is ambiguous, report the exact missing information.
5. Classify failures by evidence: actual code regression, environment failure, known flake, conflict, or unavailable required check. Run the real reproducer and narrow relevant gate before making a fix. When repair is in scope, update the branch locally by merging its base and resolve any conflict with the **resolving-merge-conflicts** skill. Rebasing or restacking rewrites history, so use it only when the user asked for history editing; when the repository's documented method requires a rebase and no such request exists, prepare the rebase and treat it as an approval gate. Pushing the result, and any force-push after an approved rebase, needs its own approval. Never delete a check, weaken an assertion, or churn code to quiet a bot. An environment or upstream failure that the shipped artifact would also hit is a product defect; apply the upstream rule in CLAUDE.md (Authorization and ownership).
6. Triage automated review findings skeptically through references/review-bot-triage.md. Prove real issues and concrete disproofs against the current code. An unresolved security/auth/billing/data/migration concern is not dismissed by a generic pattern. The watcher calls automated signals isAutomatedReview and automatedReviewPasses; these are evidence, not independent verdicts.
7. Fix real findings in the lowest unmerged unit that owns the code, with a failing regression when a cheap real test exists. Carrying that fix into upper units uses merges by default; restacking them is history editing under step 5's rule. Run relevant gates, clean-code and review-comments, then obtain the fresh-context review warranted by the change. A patch-changing head needs affected verification again.
8. Prepare approved remote operations using GitHub CLI. Put multiline text in a file. A GitHub review-comment reply uses `gh api --method POST "repos/<owner>/<repo>/pulls/<pr>/comments/<comment-id>/replies" --input <payload.json>` with the body encoded as JSON data. Do not invent a `gh pr thread` command. Posting and resolving a thread are separate authorized writes; a local disproof can be delivered without posting it.
9. Report merge-ready only when the real required checks, independent evidence and review gates are satisfied at the exact head. Pass to shipping for an explicitly approved landing. A status-only request ends with the status answer and does not edit files or publish anything.

Choose execution through [the execution reference](../references/execution.md). A status snapshot is a deterministic query, and CI waiting uses a supervised watcher. Substantial repair and verification can use a bounded native cycle; small fixes can run directly or through ordinary delegation. Use an independent read-only context for consequential verification. One owner performs changes to a shared stack. Actual run/task state and receipts establish liveness; messaging a completed agent would resume it and is not a probe. End a native run before a missing authorization or user decision.

**Reply.** Requested mode, PR/frontier and head, checks and review status, evidence-backed fixes or dismissals, and concrete blockers or proposed actions. Use real PR links and concise changes since the last report.
