### Pause safely

**Leave a checkpoint a fresh session can resume.** Pause only on an explicit pause request or an unavoidable session boundary. "Going to bed, keep going" remains an instruction to continue.

1. Finish the current atomic step, or restore its known-good state when that discards no in-progress work. When the user withdraws authorization for that step's work, or the step's work depends on withdrawn work, do not finish it. When the step cannot be finished or restored that way, or it is withdrawn or blocked by withdrawal, leave a half-done operation, such as a rebase, as it is, because aborting it would discard its in-progress work. Step 4 records it in the resume note, marked withdrawn or blocked by withdrawal when either applies. Start nothing new. Ask active children to reach a safe boundary and return their owned files and evidence; do not abruptly kill a writer mid-update. A message reaches a running child at its next tool round. If the child finishes first, the message may start a follow-up turn with a second result, or be lost, per the execution reference. If the child returns without acknowledging the stop, wait for a second result until its deadline. If no result acknowledges the stop by then, inspect that child's worktree and stop any processes it started. Use stop controls on a running writer only after its deadline passes, or at once when the user withdraws authorization for the child's work, the child's work depends on withdrawn work, or the session boundary arrives first. A pause request alone does not withdraw authorization. Stop only the monitors and processes this run owns.
2. Do not create a PR, deploy, delete, post, or mutate an external service merely to pause. Pushing a checkpoint to a branch this task created is allowed. Any other remote action needs existing approval for the exact action. Disabling an armed auto-merge on withdrawn or blocked-by-withdrawal work, or reporting a queued PR, as the [Withdrawn resume mark](#resume-marks) says is not a pause action and follows that mark.
3. Keep work durable on disk. Commit a clean checkpoint, marked work-in-progress in the repository's commit convention, with the **commit-agent** agent, scoped to this run's exact owned edits. When this task created a branch, push the checkpoint to it, unless that branch's PR has auto-merge armed or sits in a merge queue; then keep the checkpoint local and record why. When the task did not create the branch, keep the checkpoint local. Do not collect unrelated user or worker changes. When the owning playbook requires review before a commit, commit only diffs that passed that review. Work whose authorization the user withdrew, or that depends on withdrawn work, gets no checkpoint commit or push. Leave all of these uncommitted and list their files in the resume note with their [resume marks](#resume-marks). Mark a file withdrawn when its authorization was withdrawn, blocked by withdrawal when it depends on withdrawn work, and unreviewed otherwise. Also mark unreviewed each withdrawn or blocked-by-withdrawal file that has not passed that review. If the code is not commit-ready, preserve the working files and record the failing gate rather than creating a broken catch-all commit. When step 1 left an operation in progress in a worktree, make no checkpoint commit there, and list that worktree's owned files in the resume note. An edit the owning skill leaves uncommitted, such as architect's or arena's requested prose without implementation, gets no checkpoint commit; list it in the resume note as left uncommitted by that skill's rule, so a resumed session commits it only when that rule allows (architect's sketch: once architect's Phase D commit rule allows, through the governing playbook; requested prose without implementation: never, unless the user asked). Architect's sketch counts as such an edit until Phase D has implemented all of it, wherever it lives, including sketch files Phase D has already brought into the implementing tree: a checkpoint holds none of it until then. Copy every artifact a skill keeps in the OS temporary directory that the run still needs, such as architect's design directory and arena's run directory and sketch workspaces, to step 4's fallback location (under `claude-pause/`, which git never tracks) even when the note lives in a task-artifact directory, and link the copies from the note so a resumed session works from them. Never push a checkpoint from an arena candidate worktree other than the picked base, including before a base is picked.
4. Write a resume note in the named task-artifact directory. Without such a directory, use a location that survives a reboot and that git never tracks: `$(git rev-parse --path-format=absolute --git-common-dir)/claude-pause/<branch, or the short commit hash when HEAD is detached>/`, which every worktree of the repository shares, or `<profile>/claude-pause/<task name>/` under the active profile's directory when there is no repository. The branch folder depends on the worktree that wrote the note, so readers check every note under `claude-pause/`. When the note lives in a named task-artifact directory and step 1 left an operation in progress in a repository, also write a one-line pointer to the note under that repository's `claude-pause/` directory. Neither fallback location syncs to another machine. Return the resolved absolute path. Capture intent, verified progress, current branch/head, owned uncommitted files, any half-done operation left in place and whether it is withdrawn or blocked by withdrawal, each withdrawn or blocked-by-withdrawal change with its branch, PR, and any armed auto-merge or queue entry, running/stopped agents and processes, blockers, key evidence, and the first next action. For native workflows include the session ID, run ID, generated script path, arguments, and unresolved result units. Link an existing decision trail and exact-head receipts rather than duplicating them into a completion inbox. Record self-paced checks and background process monitors to restart on resume, and fixed cron tasks to inspect before creating replacements. Do not promise workers or workflow execution will survive exit; use [the execution reference](../references/execution.md) when reconstructing remaining work.

**Reply:** current phase, durable artifact paths, scoped commit or uncommitted state, any operation left in progress and whether it is withdrawn or blocked by withdrawal, each withdrawn or blocked-by-withdrawal change with its auto-merge or queue state, verification gaps, and the first action on resume.

#### Resume marks

A resume note, or a program or project ledger, can mark files, half-done operations, and whole changes or units with their branches and PRs. Any later session that finds them honors the marks, whichever playbook or skill it runs:

- **Withdrawn.** Do not continue the work. Leave its files, any half-done operation such as a merge or rebase, its branch, and its PR (pushes, CI reruns, edits, replies, merges) untouched until the user authorizes the work again. This holds even when an in-progress merge or rebase would otherwise route to resolving-merge-conflicts. The one exception is an auto-merge armed on its PR. Disable it when the task owns the PR, with `gh pr merge <pr> --disable-auto`, unless the user's latest message only asks a question or requests a read-only result and nothing earlier in this task (a standing grant, an autopilot or orchestrate run, or a babysit mode other than `check`) already authorizes pushes or edits to that PR. Recall only reports it. Otherwise report it with that command ready. The withdrawal itself does not cancel this exception. Report a PR already in a merge queue as queued, with `gh api graphql -f query='mutation{dequeuePullRequest(input:{id:"<pr node id>"}){clientMutationId}}'` ready. A withdrawal the user states in the conversation counts the same as a withdrawn mark.
- **Unreviewed.** Run the owning playbook's review before committing.
- **Blocked by withdrawal.** The work depends on withdrawn work. Hold it the same way until the withdrawn work is authorized again. Work that depends on a withdrawal stated in the conversation, or that sits above a withdrawn PR in a stack, counts as blocked by withdrawal without a recorded mark. Other blocked or `verifier-blocked` ledger entries are ordinary gaps, not this mark.

When the user authorizes withdrawn work again, update or remove its mark and its dependents' blocked-by-withdrawal marks in every resume note, pointer, and ledger that records them, including `orch unit set` states. Restore each such plan phase's recorded prior status, and set each such orch unit back to the prior state recorded in `overview.md`; a prior `running` becomes `pending`, and a phase or unit that another withdrawal still blocks becomes blocked by withdrawal (`blocked` with its resume mark for a plan phase, as multi-phase-plan says; `blocked-by-withdrawal` for an orch unit), and one that only an ordinary gap blocks becomes `blocked`. When a decision trail recorded the mark, append a row that supersedes it rather than editing the log. Mark each such file unreviewed unless it already passed the owning playbook's review.

Find notes in any named task-artifact directory, under each repository's `claude-pause/` as step 4 describes, and under `<profile>/claude-pause/` when there was no repository. Check every note in those folders, and read any ledger the earlier run kept.
