# Author a skill

Create the smallest reusable instruction set that changes an agent's decisions for the actual task. Assume the agent already knows ordinary engineering. Preserve the user's scope and approval boundaries; a skill must not imply permission for external actions or unrelated profile edits.

1. Inspect existing skills and repository conventions before creating a new one. Update the real existing home when it covers the workflow. Do not introduce abstractions or auxiliary files without a concrete use.
2. Use a lowercase-hyphen directory under project .claude/skills/ for project-specific work, or the active profile's skills/ directory when the user requested a personal skill. Resolve the active profile using the loaded profile CLAUDE.md's resource definition: CLAUDE_CONFIG_DIR when set, otherwise the directory containing that CLAUDE.md. Skill creation does not authorize changing a user's personal profile unless that is the requested scope.
3. Write SKILL.md with YAML frontmatter containing name equal to the folder and one description scalar that says what the skill does and when to use it. Use native optional fields only when required: argument-hint, allowed-tools, disable-model-invocation, user-invocable, context, agent, model, effort, hooks, paths. Never use another harness's UI metadata or invent a built-in skill. Omit model and effort unless the user explicitly requests a different policy so this profile's model and effort ceiling remain effective.
4. Keep the entrypoint focused. Put substantial conditional procedures or schemas in references/; put deterministic repeated work in scripts/; put output templates in assets/ only when needed. Link each resource from its caller and explain when it is read. Remove placeholders, duplicated instructions, setup guides, and orphaned resources.
5. In invoked SKILL markdown, use ${CLAUDE_SKILL_DIR} for bundled resource paths. That expansion does not occur in referenced documents or CLAUDE.md. Resolve resources before assigning them to workers. Let the main coordinator choose execution through [execution guidance](${CLAUDE_SKILL_DIR}/../../references/execution.md). A domain skill defines its stages, evidence, and acceptance criteria rather than repeating scheduler APIs. Worker role prompts bound the assignment and prohibit rerouting or launching the enclosing procedure. Omit runtime mechanics from each skill when the shared guide already owns them.
6. When the workflow crosses a real boundary, validate it with a realistic happy path, an edge case, and the regression that matters. Prefer existing real dependencies and fixtures. A regex that restates the skill's wording does not prove behavior. A complex skill gets an independent fresh-context evaluation using only the skill and raw task artifacts; keep evaluation outputs in a temporary workspace and within existing authorization.
7. Validate frontmatter as YAML, the folder/name relationship, resource resolution, and native metadata before declaring done. Run any existing native or repository validator, and run changed scripts through the project's package manager. Do not add a validator or dependency to the project or profile without approval; throwaway installs outside both follow the profile's toolchain rules. Document unavailable checks honestly.

Use the bundled edit-prose skill for final instructions. A discoverable skill normally permits automatic selection. Use disable-model-invocation: true when the user requests explicit-only invocation. When porting an explicit-only helper into an automatically routed workflow, resolve that intent before preserving its old flag. user-invocable: false hides a helper from slash-command menus; it is a separate choice.

Report the skill path, what requests it handles, the resources it needs, and validation evidence. Do not self-install integrations, schedule jobs, or collect unrelated transcripts.
