### Shipping

Independently verify a green stack, then land only its contiguous approved and verified run from the bottom. CI green does not establish safety, and a bot approval does not replace independent review.

1. Read the real PR/base/head graph with Git and `gh`. Choose one owner for integration. Confirm the requested landing operation and its explicit authorization; otherwise prepare the reviewable result and exact command.
2. Obtain a fresh independent per-PR verdict using [the execution reference](../references/execution.md). A substantial verification batch can use native orchestration; a small stack needs only bounded ordinary delegation. Supply actual parent/head relationships and required checks to every verifier, and keep shared live UI or measurement resources under one owner. Each verifier reads its diff, checks the relevant real behavior against parent and head, and inspects the recorded receipts. The verdict uses the execution reference's statuses: PASS (with any non-blocking observations that are not defects listed), ISSUES, BLOCKED, or INCONCLUSIVE, with evidence and a confidence label for uncertainty. Only PASS is landable. Missing or failed results remain gaps. Do not post that report remotely without authorization.
3. Resolve every actual defect. A note cannot hide a failed requirement. Distinguish non-blocking observations from failures and explain why dismissed findings do not apply.
4. Check all required checks and approvals on the exact current head. Include unit/edge/regression coverage and real UI verification when appropriate. Measure performance when a requirement or concrete risk warrants it. Unavailable checks remain blocked, never assumed passing.
5. Before a landing step, re-read the current base/head state. Record each verdict's head SHA, base SHA, and the stable `git patch-id` of its base-to-head diff, then compare against the current patch. A changed patch voids its old verdict unless the noise rule below applies. A rebase may preserve a verdict only when stable patch IDs prove identical changes, its new parent is already verified, and the verdict's environment and behavioral assumptions still hold. When the patches differ only in tests, docs, or lint configuration, build what each verification lane ran twice at the verdict SHA and once at the current head; a difference that also appears between the two verdict-SHA builds, or that is only an embedded commit SHA, is noise. If only noise differs, the lane's result stays valid, and checks and a review of the changed files still run fresh. A lane with no build output, such as a dev-server check, cannot use this rule; rerun it. Otherwise re-check the affected area. Never accept matching commit messages or a green check from an older SHA as a substitute.
6. Prepare only the bottom PR. Fetch current trunk, update the lowest verified branch against it when needed, and retarget only that PR to trunk with `gh pr edit <pr> --base <trunk>`. Push and retarget directly when the task created that branch, or the user authored and handed it over, following babysit step 5 for history rewrites and force-pushes. Otherwise run them under the landing grant, or prepare them and ask. Re-run step 5 after any push. Do not retarget, arm, or merge descendants yet.
7. Land one PR at a time: the lowest approved PASS unit, using the repository's documented merge method and GitHub CLI. Arm auto-merge (`gh pr merge <pr> --auto --squash`, or `--merge` or `--rebase` to match the repository's method) only when the user asked for merge-when-ready, and only on that PR. State the exact remote-mutating command unless the operator already supplied it. Never use a blanket loop or bypass mode as authorization for a later write. End the current native run before a missing action grant; the coordinator handles the next authorized landing stage after resolution.
8. Do not read GitHub's `autoMergeRequest` as stack readiness. It says only that auto-merge was requested for one PR; it does not prove a descendant is queued, a verdict is current, or the stack is safe.
9. Watch the current frontier until it merges or fails, without mutating the queue around it. A watcher run with `bun "<profile>/tools/workflow/watch-pr/watch-pr.ts" --owner <owner> --repo <repo> --queued-stack --stack-prs <bottom> --timeout <seconds>` is only a wake signal here, supervised like any bounded watch. When it exits with a `BLOCKER`, poll `gh` once and back off before re-arming. After each wake, poll `gh pr view <pr> --json state,mergedAt,mergeStateStatus,statusCheckRollup,autoMergeRequest` and treat the PR as landed only when `mergedAt` is set or `state` is `MERGED`. Do not use Babysit's queued `WAITING`/`merge-queue` stop here. It has failed only when `state` is `CLOSED` with no `mergedAt`, a required check concludes `FAILURE`, `CANCELLED`, `TIMED_OUT`, `ACTION_REQUIRED`, `STARTUP_FAILURE`, or (for a status context) `ERROR` and blocks merge with no auto-merge pending, or `mergeStateStatus` is `UNSTABLE` or `DIRTY` with no auto-merge pending. `BLOCKED` while checks are pending or auto-merge is armed is not failure. If the queue stalls, diagnose before mutating anything.
10. After landing, fetch trunk, confirm the merged SHA is present, and inspect the new bottom PR's base, head, checks and patch-id. A host may retarget a child automatically; do not assume it did. Restack or retarget the remaining upper PRs after a landing when the task created their branches and nobody else has pushed to them, using `--force-with-lease=<branch>:<sha you rewrote from>`, and report it. When someone else has pushed to a branch the task created, update it by merging, push fast-forward commits, and retarget its PR. Restacking a branch the user authored and handed over follows babysit step 5, and retargeting its PR proceeds because the task owns that PR. For a branch someone else owns, prepare it and obtain approval unless the landing grant already covers it. Repeat from step 5 for that one PR. Stop at the first failed, stale, blocked or unapproved unit; do not skip upward.
11. Reconcile receipts and report landed versus merge-ready/unverified work, the next unverified PR, and what verifying it would take. Keep the local ledger and decision trail accurate.

For a Graphite-managed stack, use its existing authoritative metadata and the optional bundled frontier command only when `gt` is already available. This playbook's PR operations use `gh`; it does not require an alternative forge client.

**Reply.** Verified stack order and heads, landed PRs with real links, receipts used, patch-equivalence evidence if reused, and exact blocked or remaining actions.
