### Autopilot-full

Drive independent change requests through implementation and exact-head verification. Merge only those actions the user explicitly authorized. Use autopilot-stack when the operator wants one dependent stack to review and land.

1. Frame the queue, independence/dependency graph, completion predicate, allowed changes and action grants. Check whether one ordinary autonomous run is sufficient before creating a program.
2. Choose execution through [the execution reference](../references/execution.md). Use bounded native batches for a substantial set of independent changes, followed by checks and review; one small change can run directly or with ordinary delegation. Assign one owner per change, inheriting the configured model and effort. Give writers independent worktrees or strictly disjoint scopes. Explicitly base a dependent owner on the parent's actual head rather than an automatically chosen remote default branch.
3. Each owner builds its change, runs the relevant real checks, starts a show-me-your-work trail, applies clean-code, and returns its branch, worktree path, diff, trail path, evidence and any findings outside its ownership or blocked, with its changes left uncommitted. Owners cannot delegate, so the coordinator runs review-comments (with its independent comment-reviewer) and the trail's independent review on each returned diff, then runs the commit-agent agent in that worktree and records the resulting head SHA. An early local commit through the same route is fine when useful; a private local result is a valid deliverable while publication approval is pending.
4. Create a PR through opening-a-pr only after the user requests or approves that action. Use GitHub CLI and the requested base/draft state. Observe checks and review threads through babysit; unauthorized replies, edits and pushes remain prepared actions, not implicit loop permissions. End the current native run before a missing authorization or user decision, then start the next stage after it is resolved.
5. At each code-ready head, run independent verification through swarm under the selected execution method. Include configured build/lint/type/test gates, behavior and edge cases, the real UI when applicable, and performance checks when warranted. Scale lanes to the risk, with one owner for live UI and shared measurement resources. Reviewers inspect the diff and receipts; they do not trust the PR body as proof.
6. Send real findings to the owner. A patch-changing head needs affected checks and a fresh independent verdict. A pure rebase may reuse a receipt only when patch-id equivalence and unchanged assumptions are established under shipping.
7. The coordinator audits current-head evidence before merge-ready. Merge is never an owner-only decision. Perform an approved merge through shipping, or stop at the concrete merge-ready result and command for the operator.
8. Reconcile every spawned child, the queue and its evidence. Confirm the done predicate without weakening it. Missing access or authorization is a recorded blocker, not a successful merge.

Native execution owns active workers, dependencies, retries, and results; Tasks displays coarse milestones, while the program ledger retains cross-run change facts and exact-head receipts. Do not maintain a duplicate dispatch queue or completion inbox. Account for every launched worker, including failed or missing results. Supervise expected artifacts and deadlines without resuming a child to inspect liveness. Assign one writer to each shared branch. Stop all writes when the user pauses or withdraws authorization.

**Reply.** Queue result, verified heads and artifact paths, approved actions completed, findings fixed, and the exact remaining gates. Include only real PR links created or read during the run.
