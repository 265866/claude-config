### Shipping

Independently verify a green stack, then land only its contiguous approved and verified run from the bottom. CI green does not establish safety, and a bot approval does not replace independent review.

1. Read the real PR/base/head graph with Git and `gh`. Choose one owner for integration. Confirm the requested landing operation and its explicit authorization; otherwise prepare the reviewable result and exact command.
2. Obtain a fresh independent per-PR verdict using [the execution reference](../references/execution.md). A substantial verification batch can use native orchestration; a small stack needs only bounded ordinary delegation. Supply actual parent/head relationships and required checks to every verifier, and keep shared live UI or measurement resources under one owner. Each verifier reads its diff, checks the relevant real behavior against parent and head, and inspects the recorded receipts. The verdict uses the execution reference's statuses: PASS (with any non-blocking observations that are not defects listed), ISSUES, BLOCKED, or INCONCLUSIVE, with evidence and a confidence label for uncertainty. Only PASS is landable. Missing or failed results remain gaps. Do not post that report remotely without authorization.
3. Resolve every actual defect. A note cannot hide a failed requirement. Distinguish non-blocking observations from failures and explain why dismissed findings do not apply.
4. Check all required checks and approvals on the exact current head. Include unit/edge/regression coverage and real UI verification when appropriate. Measure performance when a requirement or concrete risk warrants it. Unavailable checks remain blocked, never assumed passing.
5. Before a landing step, re-read the current base/head state. A changed patch voids its old verdict. A rebase may preserve a verdict only when stable patch IDs prove identical changes, its new parent is already verified, and the verdict's environment and behavioral assumptions still hold. Otherwise re-check the affected area.
6. Land the lowest approved PASS unit first using the repository's documented merge method and GitHub CLI. State the exact remote-mutating command unless the operator already supplied it. Never use a blanket loop or bypass mode as authorization for a later write. End the current native run before a missing action grant; the coordinator handles the next authorized landing stage after resolution.
7. After landing, confirm the real result, head/base relationships and required checks. Capture any new stack generation and verify the next eligible unit. Restacking or retargeting the remaining upper PRs after a landing rewrites history and mutates the remote, so prepare it and obtain approval unless the landing grant already covers it. Stop at the first failed, stale, blocked or unapproved unit; do not skip upward.
8. Reconcile receipts and report landed versus merge-ready/unverified work. Keep the local ledger and decision trail accurate.

For a Graphite-managed stack, use its existing authoritative metadata and the optional bundled frontier command only when `gt` is already available. This playbook's PR operations use `gh`; it does not require an alternative forge client.

**Reply.** Verified stack order and heads, landed PRs with real links, receipts used, patch-equivalence evidence if reused, and exact blocked or remaining actions.
