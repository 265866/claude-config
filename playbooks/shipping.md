### Shipping

Independently verify a green stack, then land only its contiguous approved and verified run from the bottom. CI green does not establish safety, and a bot approval does not replace independent review.

1. Read the real PR/base/head graph with Git and `gh`. Read every unresolved landing record a previous run left for a PR in this stack, including its merged PRs (a record that names a PR in this stack counts), wherever step 9 keeps them: the project or run ledger, `overview.md` for an orchestrate program, or a resume note found as the [Resume marks](pause-safely.md#resume-marks) section describes, including through a `claude-pause/` pointer. After the rest of this step, for a PR one records as landed unverified, or as landed or probably landed with its head unverified, poll it once as step 9 reads the state. When that poll establishes Landed and supplies `headRefOid`, run step 9's Landed head check against the recorded verified head, then step 10, for that PR before preparing anything above it. When the poll shows the PR open, treat it as unlanded: with the landing grant, handle any auto-merge or merge-queue entry an earlier run left as step 9's Stopped bullet does, otherwise report it with the command ready, and land nothing above it until it lands. Otherwise land nothing above it. For a PR recorded as landed with a defect, land nothing above it until steps 2 and 5 confirm at the current trunk head that the defect is gone, then run step 10 for it; the one exception is a PR whose head carries the fix, which may land once steps 2 and 5 confirm at that head that the defect is gone. After that PR lands and step 9's head check passes, confirm at the new trunk head per steps 2 and 5 that the defect is gone, which is the trunk-head confirmation, then run step 10 for the defective PR. Step 11 resolves each record once it passes. Check the [resume marks](pause-safely.md#resume-marks) for every PR in scope. Hold a withdrawn or blocked-by-withdrawal PR and its branch as that mark says, including its armed auto-merge or merge-queue entry, before landing anything below it. When its auto-merge stays armed, or it stays in a merge queue, because the mark only lets you report it, stop before landing anything below it and ask the user. Land only below it. Choose one owner for integration. Confirm the requested landing operation and its explicit authorization; otherwise prepare the reviewable result and exact command.
2. Obtain a fresh independent per-PR verdict using [the execution reference](../references/execution.md). A substantial verification batch can use native orchestration; a small stack needs only bounded ordinary delegation. Supply actual parent/head relationships and required checks to every verifier, and keep shared live UI or measurement resources under one owner. Each verifier reads its diff, checks the relevant real behavior against parent and head, and inspects the recorded receipts. The verdict uses the execution reference's statuses: PASS (with any non-blocking observations that are not defects listed), ISSUES, BLOCKED, or INCONCLUSIVE, with evidence and a confidence label for uncertainty. Only PASS is landable. Missing or failed results remain gaps. Do not post that report remotely without authorization.
3. Resolve every actual defect. A note cannot hide a failed requirement. Distinguish non-blocking observations from failures and explain why dismissed findings do not apply.
4. Check all required checks and approvals on the exact current head. Include unit/edge/regression coverage and real UI verification when appropriate. Measure performance when a requirement or concrete risk warrants it. Unavailable checks remain blocked, never assumed passing. A head with no checks at all, as babysit step 10's exit-7 exception establishes, has none to wait for; a required check that never reported stays unavailable. A head with no checks, approvals met, no conflict, and no unresolved review threads that still shows `mergeStateStatus` `BLOCKED` stays blocked; report it as an unidentified required gate (a check that never reported, or another branch-protection or ruleset rule), reading `gh api repos/<owner>/<repo>/rules/branches/<base>` and `gh api repos/<owner>/<repo>/branches/<base> --jq .protection.required_status_checks` for the cause. Pending checks are a wait, not a block. Wait for them as babysit step 10's first BLOCKER sub-rule says: a bounded single-PR watch (babysit step 3), and while it reports exit 3 or 6 with checks still pending, poll `--status-only` at the watcher's interval within the deadline.
5. Before a landing step, re-read the current base/head state. Record each verdict's head SHA, base SHA, and the stable `git patch-id` of its base-to-head diff, then compare against the current patch. A changed patch voids its old verdict unless the noise rule below applies. A rebase may preserve a verdict only when stable patch IDs prove identical changes, its new parent is already verified, and the verdict's environment and behavioral assumptions still hold. When the patches differ only in tests, docs, or lint configuration, build what each verification lane ran twice at the verdict SHA and once at the current head; a difference that also appears between the two verdict-SHA builds, or that is only an embedded commit SHA, is noise. If only noise differs, the lane's result stays valid, and checks and a review of the changed files still run fresh. A lane with no build output, such as a dev-server check, cannot use this rule; rerun it. Otherwise re-check the affected area. Never accept matching commit messages or a green check from an older SHA as a substitute.
6. Prepare only the bottom PR. Fetch current trunk, update the lowest verified branch against it when needed, and retarget only that PR to trunk with `gh pr edit <pr> --base <trunk>`. Retarget directly when the task owns the PR. Push directly when the task created that branch, or the user authored and handed it over, unless it is a default or protected branch, following babysit steps 1 and 5 for that update's pushes, history rewrites, and force-pushes. Otherwise run those pushes, and the retarget of a PR the task does not own, under the landing grant when it covers them, or prepare them and ask. Re-run steps 4 and 5 after any push or retarget. Do not retarget, arm, or merge descendants yet.

   Once the PR targets trunk, and before step 7, work out which issues the merge closes, now or later.

   - **Where a closure comes from.** GitHub closes an issue when a closing keyword reaches the default branch in a commit message. It also closes one when a PR that targets the default branch merges with the keyword in its body or with a manual link to the issue. `closingIssuesReferences` lists only those body keywords and manual links, and only for a PR that targets the default branch.
   - **What lands in a commit message.** A merge or a rebase lands the PR's commit messages unchanged. A merge commit or a squash commit carries the step 7 `--subject` and `--body` when they are passed. Otherwise, or through a merge queue, it carries GitHub's default text, which follows the repository's merge and squash settings. A merge commit's default text comes only from the PR title, the PR body, and a `Merge pull request #<number> from <head owner>/<head branch>` subject. Read the default text with `gh api graphql -f query='query{repository(owner:"<owner>",name:"<repo>"){pullRequest(number:<pr>){viewerMergeHeadlineText(mergeType:<method>) viewerMergeBodyText(mergeType:<method>)}}}'`, where `<method>` is `MERGE` or `SQUASH`. Run it with the `gh` account that runs step 7, after the PR's last push and its last title or body edit. It works without write access to the repository.
   - **Find the issues.** Read the PR's commit messages, title, and body, and use the rules above to decide which keywords land in a commit message. When trunk is the default branch, also run `gh pr view <pr> --json closingIssuesReferences`. When trunk is not the default branch, this merge closes nothing now. Tell the user that, and that each keyword landing in a commit message closes its issue only once a commit carrying it reaches the default branch. When you cannot tell whether a keyword lands, count it as missing for a requested issue this PR carries the fix for, and as landing for any other issue.
   - **Issues the user asked to close.** This covers each requested issue that this PR carries the fix for. A requested issue that a PR below this one in the stack already fixed counts as approved, so keep its keyword or link. A requested issue that a later PR in the stack fixes waits until that PR is the bottom. When this PR names such an issue, note whether it is open, remove that closure as Removing a declined closure says, without asking whether to close the issue, and check it in step 10 like a declined one. If the user keeps a manual link for it, tell them this merge will close the issue before its fix lands. When trunk is the default branch and neither `closingIssuesReferences` nor a keyword that lands names a requested issue this PR carries the fix for, add a closing keyword for it to the PR body when the task owns the PR. Then wait about a minute and check once more. If it is still missing, tell the user the merge may not close it and that linking the PR from the issue's Development sidebar fixes that. Then wait until they link it, the PR changes so that it names the issue, or they accept that the issue stays open. When trunk is not the default branch and no landing keyword names a requested issue this PR carries the fix for, tell the user it will not close, then wait until they accept that or the PR changes so that a keyword for it lands.
   - **Issues the user did not ask to close.** Name each one, note whether it is open, and get the user's approval before step 7. A landing grant that does not name that issue does not cover closing it. A decline stays in force for later PRs in the stack, so do not ask again whether to close that issue. Still remove its keyword or link from each later PR.
   - **Removing a declined closure.** This also covers a requested issue that a later PR fixes, and a declined keyword below includes its keyword. Remove a keyword from the PR body and title. Edit the PR directly only when the task owns it, as CLAUDE.md defines it, and otherwise ask. Unlinking a manual link changes the issue, a record others use, so ask the user to unlink it from the issue's Development sidebar, as with adding one. Then wait until they unlink it or tell you to keep it. Removing the keyword from the PR covers a merge commit's own text. For a squash, pass `--subject` and `--body` on the step 7 command, including an `--auto` one. Start from GitHub's default squash text, read as above after the PR edits. Then remove only the declined keywords, and make sure a closing keyword still lands for each requested issue this PR carries the fix for. A merge or rebase still lands the PR's commit messages unchanged, and a merge queue ignores `--subject` and `--body`. In those cases, when the task created the PR's branch and nobody else has pushed to it, reword each commit whose message lands, per the rules above, and carries a declined keyword. Drop only the declined keywords. This needs only that ownership, not babysit step 5's condition that the repository's documented method requires a rewrite or the rewrite gives a clearer history. Push with `--force-with-lease=<branch>:<sha you last pushed to it>`, then re-run this playbook's steps 4 and 5. When the task does not own the branch that way, ask the user how to proceed. A descendant branch may still hold the original commits, so this step checks them again when its PR becomes the bottom.
7. Land one PR at a time: the lowest approved PASS unit, using the repository's documented merge method and GitHub CLI. Arm auto-merge (`gh pr merge <pr> --auto --squash`, or `--merge` or `--rebase` to match the repository's method) only when the user asked for merge-when-ready, and only on that PR. State the exact remote-mutating command unless the operator already supplied it. When step 6 requires `--subject` and `--body`, add them to an operator-supplied command too, and state the final command before you run it. Never use a blanket loop or bypass mode as authorization for a later write. End the current native run before a missing action grant or user decision; the coordinator handles the next authorized landing stage after resolution. If GitHub refuses a direct merge, handle it as step 9's Stopped outcome; never add `--admin`.
8. Do not read GitHub's `autoMergeRequest` as stack readiness. It says only that auto-merge was requested for one PR; it does not prove a descendant is queued, a verdict is current, or the stack is safe.
9. Watch the current frontier until it lands or stops, without mutating the queue around it. A watcher run with `bun "<profile>/tools/workflow/watch-pr/watch-pr.ts" --owner <owner> --repo <repo> --queued-stack --stack-prs <bottom> --timeout <seconds>` is only a wake signal here. Each step 7 command starts a new step 9 deadline; pass every watcher run a `--timeout` no longer than the seconds left, and under one second left means the deadline has passed. Keep one watcher at a time and leave a running one alone. Poll at every wake and watcher exit; after an exit, back off for the watcher's `--interval` (60 seconds by default, capped at the seconds left) before re-arming. Do not use Babysit's queued `WAITING`/`merge-queue` stop here. Each poll reads `gh pr view <pr> --json state,mergedAt,headRefOid,mergeStateStatus,autoMergeRequest,reviewDecision,isDraft`, `gh pr checks <pr> --required --json name,state,bucket,link` (an exit 1 reporting no checks or no required checks means none is failing), and `gh api graphql -f query='query{repository(owner:"<owner>",name:"<repo>"){pullRequest(number:<pr>){state mergedAt headRefOid isMergeQueueEnabled isInMergeQueue timelineItems(itemTypes:REMOVED_FROM_MERGE_QUEUE_EVENT,last:1){nodes{... on RemovedFromMergeQueueEvent{reason createdAt}}}}}}'`. A queued PR shows no `autoMergeRequest`. If any read fails for another reason, the poll has failed. Landed, or a Stopped cause the successful reads establish on their own (a closed PR, a changed head, `DIRTY`, a newer non-`merged` removal event, or an auto-merge someone else disabled when the GraphQL read succeeded and shows the PR outside the merge queue), still applies; otherwise no outcome applies, so retry at the next wake. After the deadline, retry once after the watcher's `--interval`. If it fails again and any watcher run since the latest step 7 command exited `COMPLETE`, report the PR as probably landed with its head unverified, record it, its verified head, and its step 6 closure decisions as a landing record, and stop the landing at this PR. Otherwise take Stopped for the deadline and report the failed read, running `gh pr merge <pr> --disable-auto` when step 7 armed auto-merge unless successful reads showed it gone and the PR not queued. If that disable fails, or the GraphQL read failed and no successful read in this step 9 showed `isMergeQueueEnabled` false, report that auto-merge may still be armed or the PR queued, with the disable command and the Withdrawn mark's dequeue mutation ready (its node ID from `gh pr view <pr> --json id`). The verified head is the head steps 4 and 5 last passed on before the latest step 7 command. A landing record goes in the run's ledger (for an orchestrate program, `overview.md`, because `ledger.tsv` holds only verdicts) or, without one, in a resume note as Pause safely step 4 describes, and names the PRs of its stack. When the record is kept outside the repository's `claude-pause/`, also write a one-line pointer there, labeled as a landing-record pointer. A required check has failed when it is in the `fail` or `cancel` bucket or its state is `STARTUP_FAILURE`. Then take the first outcome that matches:

    - **Landed.** Either read shows `mergedAt` set or `state` `MERGED`, or the latest removal event has reason `merged` and is newer than the latest step 7 command. Go to step 10, even after the deadline. Both reads carry `headRefOid` (after a merge it is the PR's last head); if neither supplied it, retry under the failed-read rule, and once the deadline's single retry also fails, report the PR as landed with its head unverified, record it, its verified head, and its step 6 closure decisions as a landing record, and stop the landing at this PR. When the merged `headRefOid` differs from the verified head, report it as landed unverified, record it as landed unverified, with its verified head, and its step 6 closure decisions as a landing record, verify the landed diff per steps 2 and 5, and land nothing above it until that passes or, for an ISSUES verdict, step 1's defect-record rule allows it. For an ISSUES verdict, update its landing record to landed with a defect, report the defect now on trunk, and fix it in scope: in the next stack PR when no resume mark holds it and babysit step 5's push rules allow, otherwise as a prepared fix PR, which is ask-first to open. Continue above it only as step 1's defect-record rule allows; otherwise stop the landing at this PR as step 10's stop at the first failed unit does. For a BLOCKED or INCONCLUSIVE verdict, keep it landed unverified, stop the landing at this PR as step 10's stop at the first failed unit does, and report what blocked verification.
    - **Waiting.** Before the deadline, the PR is open on the verified head; no required check has failed; it is not `DIRTY`, and not `BEHIND` unless `isMergeQueueEnabled` is true; this poll was not triggered by a watcher exit 3 for unresolved review threads; `reviewDecision` is not `CHANGES_REQUESTED` or `REVIEW_REQUIRED` and it is not a draft; and something will still merge it, because it is in the merge queue or the auto-merge step 7 armed is still armed. `BLOCKED` while checks are pending and `UNSTABLE` wait here. Keep watching.
    - **Stopped.** Anything else. That includes the deadline passing, a closed PR, a changed head, a removal from the merge queue (its latest removal event has a reason other than `merged` and is newer than the latest step 7 command), a failed required check, `DIRTY`, `BEHIND` without a merge queue, a review gate or unresolved thread, an auto-merge someone else disabled, and a direct step 7 merge GitHub refused. Stop the watcher. Disable the auto-merge step 7 armed if it is still armed, with `gh pr merge <pr> --disable-auto`. A PR still in the queue cannot be disabled that way; report it with the Withdrawn mark's dequeue mutation ready, because dequeuing it is ask-first, and recover only after the user dequeues it or approves the dequeue, since a push to a queued PR dequeues it. Then, unless the deadline is the only Stopped cause that holds, recover at most once per PR in this landing, and only when the cause is one this run can fix within scope:
        - **A failed required check, or a removal for `failed_checks` or `checks_timed_out`.** For a check on the PR, use the failing run from `gh pr checks`' `link`; for a removal, find the merge-queue run with `gh run list --event merge_group`, whose `headBranch` names the PR. Classify the failure per babysit step 6. A flake or infrastructure failure gets one fresh rerun of that workflow on the same head (a removal needs none). Once steps 4 and 5 pass, run step 7's exact command again (the same auto-merge, direct merge, or re-add, with any `--subject` and `--body`), then watch again. Any other cause takes the next bullet.
        - **A code failure, `DIRTY` or a `merge_conflict` removal, `BEHIND` without a merge queue, a changed head, or unresolved threads you own** (per babysit steps 7 and 8). Return to step 6 for this PR, fix or update it there under babysit step 5's push rules, and run step 7's command again, with the same merge method and mode and the `--subject` and `--body` step 6 now requires, only after steps 2 through 5 pass on the new head. For threads, also wait until each one is resolved; replying and resolving are ask-first, so prepare them and ask. Never add `--admin`.

    Report every other stop, and a second stop for the same PR in this landing, with its cause, the PR's state, and whether anything can still merge it, suggesting a merge queue when `BEHIND` recurs. Closing, reopening, dequeuing, and clearing a person-only gate stay with the user.
10. After landing, fetch trunk, confirm the merged SHA is present, and inspect the new bottom PR's base, head, checks and patch-id. A host may retarget a child automatically; do not assume it did. When trunk is the default branch, for each issue the landed PR was meant to close, confirm with `gh issue view <issue> --json state` that it closed. If one is still open, wait about a minute and check once more. If it is still open, report it, because closing it yourself is ask-first. When trunk is the default branch, about a minute after the merge, also confirm that each issue the user declined to close, and each requested issue a later PR fixes, that step 6 found open is still open. If one closed, find what closed it with `gh api graphql -f query='query{repository(owner:"<owner>",name:"<repo>"){issue(number:<issue>){timelineItems(itemTypes:CLOSED_EVENT,last:1){nodes{... on ClosedEvent{closer{__typename ... on PullRequest{number repository{nameWithOwner}} ... on Commit{oid}}}}}}}}'`. `<owner>` and `<repo>` name the issue's repository, and `gh issue` commands take `-R <owner>/<repo>` for it. The landed PR closed it when `closer` is the landed PR in its repository, or a commit that `gh pr view <landed PR> -R <landed PR owner>/<landed PR repo> --json mergeCommit,commits --jq '.mergeCommit.oid, .commits[].oid'` prints. When that list does not include the commit, also count it when `gh api repos/<landed PR owner>/<landed PR repo>/commits/<oid>/pulls --jq '.[].number'` lists the landed PR. This covers a rebase merge, which gives the landed commits new oids, and a PR with more than 100 commits, which `gh pr view` does not list in full. Report each closure with its evidence and `gh issue reopen <issue>` ready, because reopening it is ask-first. The landing does not need the reopen, so the reopen decision does not end the run or hold other work. Then act on what closed it:

    - **A manual link the user chose to keep after step 6 warned about it or asked them to unlink it.** Report the closure as expected and continue.
    - **Anything else in the landed PR.** Find which keyword or link step 6 missed. When step 6 runs for each later PR in this stack, also look for that kind of keyword or link naming any issue. Count it as landing, except for a requested issue that later PR carries the fix for, which keeps the Find the issues rule. Before step 7, handle each issue it names under step 6's bullets. Remove it, as Removing a declined closure says, for an issue the user declined or a requested issue a PR above that later PR fixes. Handle a requested issue that later PR carries the fix for under Issues the user asked to close. Treat a requested issue that a PR below that later PR fixed, including the landed PR, as approved, as that bullet says. Handle any other issue under Issues the user did not ask to close. If you cannot find which kind step 6 missed, stop before the next landing and ask the user.
    - **A person or another change.** Report it and continue.

    After a landing, act only on the remaining upper PRs below the lowest PR a resume mark holds. Restack them when the task created their branches and nobody else has pushed to them, using `--force-with-lease=<branch>:<sha you last pushed to it>`, and report it. When someone else has pushed to a branch the task created, update it by merging and push fast-forward commits. Restacking a branch the user authored and handed over follows babysit step 5. For a branch someone else owns, prepare the update and obtain approval unless the landing grant already covers it. When a remaining upper PR needs a retarget, authorize it as step 6 does: directly when the task owns the PR, otherwise under the landing grant when it covers the retarget, or prepare it and ask. Repeat from step 4 for the new bottom PR unless a resume mark holds it, returning to steps 2 and 3 when step 5 voids its verdict; when a mark holds it, stop the landing there and report that PR as held. Stop at the first unit that stays failed, stale, blocked or unapproved after steps 2 through 5 and step 9's recovery fix what is in scope; do not skip upward. Landing a PR under step 1's fix-carrying exception is not skipping upward.
11. Reconcile receipts and report landed versus merge-ready/unverified work, the next unverified PR, and what verifying it would take. Keep the local ledger and decision trail accurate. Mark each landing record resolved where it is kept once its head check and any landed-diff verification (for a recorded defect, instead step 1's confirmation at the current trunk head that it is gone) and step 10 have passed. Remove each landing-record pointer step 9 wrote once the ledger or note it names holds no unresolved landing record, leave every other pointer alone, and keep the ledger or note itself.

For a Graphite-managed stack, use its existing authoritative metadata and the optional bundled frontier command only when `gt` is already available. This playbook's PR operations use `gh`; it does not require an alternative forge client.

**Reply.** Verified stack order and heads, landed PRs with real links, receipts used, patch-equivalence evidence if reused, and exact blocked or remaining actions.
